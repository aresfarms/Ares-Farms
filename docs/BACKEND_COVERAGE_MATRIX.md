# Backend Coverage Matrix

This matrix records where the Ares/Furlong backend build stands before broad
frontend, borrower, lender, sponsor, marketplace, or product-module expansion.

It is written for Caitlin as the operator. You do not need to read code to use
this document.

## Governing Decision

Backend-first remains the hard rule.

The backend foundation is now complete for governed internal workflow screens
and module builds that use the completed backend surfaces listed below.

Live external calls, actual authenticated agency sessions, external notice
provider sends, production payment capture, raw document processing, public
production exposure, and sovereign data use beyond the recorded Gateway review
are no longer treated as missing backend foundation. They are controlled
module/promotion work with their own gates.

## Master Volume Alignment

This matrix follows the current Master Volume baseline recorded in:

`docs/MASTER_VOLUME_SOURCE_SNAPSHOT.md`

The local Master Volume file hashes were checked during this pass and the
recorded baseline was updated for the newest DOCX/PDF/HTML/MD files supplied by
Caitlin.

The 2026-05-31 Master Volume update adds Volume VI as the canonical source for
source intelligence, scraper governance, property discovery, revenue
intelligence, runtime governance, module integration, public source surfaces,
conformance, backend readiness, module readiness, and portable vertical surface
alignment.

The newest Batch 25 volume updates also add environmental pathway governance as
backend foundation: Environmental Engineering Spoke authority and Banker Spoke
isolation, NEPA/Phase I/II/III/state environmental assessment routing,
provider-license verification, borrower fee disclosure/autonomy protections,
audit anchors, and environmental pathway advancement gates.

The Volume VI Consolidation & Changes Summary is also active moving forward.
That means duplicated uploaded source/scraper/revenue/integration/conformance
materials are treated through Volume VI, not as separate competing build
tracks. The Build Conformance Matrix is the proof layer: each doctrine family
must point to actual routes, schema, migrations, runtime files, and a
verification command, or be explicitly recorded as blocked pending controlled
promotion.

The backend completion standard remains:

- runtime guard,
- version lineage,
- classification where data is sensitive or regulated,
- explainability where the route produces decision, report, scoring,
  recommendation, rule, review, document, connector, or borrower-facing output,
- observability,
- replay reference,
- durable governance evidence,
- record-level authorization where records are scoped to a borrower,
  application, tenant, document, review, queue, partner, report, connector,
  notice, payment, or governance object,
- audit-safe error handling,
- deterministic response shape,
- smoke-test coverage.

Security & audit readiness is now governed by:

`docs/SECURITY_AUDIT_READINESS_GATE.md`

Customer-facing claim readiness is now governed by:

`src/lib/governance/contentClaimsPolicy.ts`

This gate incorporates `Furlong_Customer_Version.pdf` and
`Furlong_Governance_Doctrines_Master_Series.pdf` for lender-ready language,
public verification claims, free borrower tier controls, borrower portability,
AI advisory-only limits, borrower-free positioning, data-use limits, and
SOC 2/FedRAMP posture honesty.
